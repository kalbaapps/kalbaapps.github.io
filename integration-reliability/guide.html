What it does

Most monitoring tells you a website is "up". But systems can all say "OK" while the data is wrong: a salary reaches payroll rounded down, a new customer never reaches billing, a webhook stops being delivered. Nobody notices until someone complains.

Integration Reliability runs small checks on a schedule. A check is a short story, for example: "Create an employee in HR, then look in Payroll. The same person must be there with the same salary." When the story stops being true you get an alert that says what went wrong and a likely cause in plain English.

There are two parts. The server runs the checks (free software you run yourself). The app on your phone shows the results and alerts you. The app does nothing on its own, so you need a server for real use.

Try it with no setup

On the app's first screen tap Try the demo. You get the full app with sample data, and nothing is sent anywhere.

  • Status: three sample checks, each with PASS or FAIL, uptime and a row of history bars. Tap Simulate a failure to make the fake integration fail.
  • The banner turns red, the first check shows the error (monthlySalary: expected 125750, got 125000) and a Likely cause box explains it.
  • Incidents: the outage appears as ONGOING. Tap Fix the fake integration on Status and it becomes RESOLVED with how long it lasted.
  • Add: paste any curl command and see how a check gets built. Settings shows the privacy policy and this guide.

What you need

  • A computer (Windows, Mac or Linux) that can stay switched on, or a small cloud server.
  • Node.js 20 or newer (free, from nodejs.org). Nothing else to install.
  • About 15 minutes the first time.

No coding is needed, but you will type a few commands into a terminal (PowerShell on Windows, Terminal on Mac).

Step 1: run your server

  1. Get the server software. While the app is in early access the server is shared as a .zip download by request (see Getting help for how to ask). Unzip it somewhere you will keep it, for example your Documents folder.
  2. Open a terminal in the unzipped folder.
  3. Start it with a password (choose a long one): 
    # Windows PowerShell
$env:APP_PASSWORD = 'choose-a-long-password'
npm start

# Mac / Linux
APP_PASSWORD='choose-a-long-password' npm start
  4. Open http://localhost:3000 in your browser. You should see the dashboard with one sample check. Click Sign in and type your password.
Without a password anyone who can reach your server can read the results, and editing only works from the same computer. Always set APP_PASSWORD if the server can be reached from outside.

The sample check uses built-in fake systems, so it passes. You can remove it later. Results are saved in the data folder next to the program. Closing the terminal stops the server.

Step 2: let your phone reach it

Your phone must be able to open your server's address. Which address works depends on the app version:

SituationWhat to enter in the app
Google Play version (needs a secure https:// address)An https:// address. The easiest way is a free Cloudflare tunnel, below.
Test/developer version on the same Wi-Fihttp://192.168.x.x:3000 (your computer's address from ipconfig or ifconfig).
Android emulatorhttp://10.0.2.2:3000

A free secure address with Cloudflare Tunnel

  1. Install cloudflared (Windows: winget install Cloudflare.cloudflared; Mac: brew install cloudflared; other systems: see Cloudflare's download page).
  2. With your server running, in a second terminal run: 
    cloudflared tunnel --url http://localhost:3000
  3. After a few seconds it prints an address ending in trycloudflare.com. That is your https:// address.
Know the limits: this free address changes every time you restart the tunnel, and it only works while your computer, the server and the tunnel are all running. For something permanent, run the server on an always-on machine and give it a proper address of your own.

Step 3: connect the app

  1. Open the app. On the first screen type your server's address (for example https://something.trycloudflare.com).
  2. Type the password you chose, then tap Connect. Leave the password empty only if you want to look around as a read-only guest on a server that allows it.
  3. You land on Status. Tap Run checks now to see the sample check pass.

To use a different server later: Settings → Change server / sign out.

Step 4: add your first check

The quickest way is a curl command. These are the example commands you find in almost every API's documentation, in Postman ("Code snippet"), and in a browser (developer tools → Network → right-click a request → Copy as cURL).

In the app

  1. Open the Add tab (you must be signed in) and paste the command, for example curl https://jsonplaceholder.typicode.com/todos/1.
  2. Tap Try it. The server calls the address once and shows the status it got. If the command contains an API key, the server stores it as a secret and hides it.
  3. Below you may see values from the answer. Tick only values that should always stay the same (like an ID or a plan name). Do not tick times, random IDs or counters that change.
  4. Tap Add this check. It now runs automatically.
Important: the address in the command is called by your server, not by your phone. It must work from the computer the server runs on.

On the web dashboard (more options)

Sign in at your server's address, click Add or change checks, then: 1 Add a check (paste curl, or pick a template such as "HR → Payroll"), 2 Your checks (use Test them to try without saving, then Save). Each check has a Runs menu (every minute up to every day). The editor also manages Secrets (API keys), Alerts, and an Advanced JSON view for multi-step checks.

To remove a check in the app: Status → Remove this check under it (you are asked to confirm).

Reading the results

You seeIt means
PASS / FAILThe latest run of that check passed or failed.
Row of small barsThe last runs, oldest to newest. Green = passed, red = failed.
"every 1m"How often the check runs.
"uptime 99.5% (7d)"Share of runs that passed in the last 7 days.
Red line under a failed checkThe step that failed and exactly what was expected versus received.
Likely cause boxA plain-English guess and what to check first. It is a hint, not a diagnosis.
Incidents tabEach outage from the moment a check started failing until it recovered. Two failing runs in a row are one incident.
"Status (1)"One check is failing right now.

Alerts and reports

Phone alerts (the app)

Sign in, open Settings → Turn on phone alerts and allow notifications. Then tap Send a test alert. You get a notification when a check starts failing and again when it recovers, not on every failing run. Phone alerts work in the installed app on a real phone.

Email, chat and reports (set on the server)

Set these before npm start (same way as APP_PASSWORD), then check them under Alerts in the web editor with Send test alert:

WhatSetting
Email through Brevo (works on networks that block mail ports)BREVO_API_KEY, ALERT_EMAIL_FROM (a sender verified in Brevo), ALERT_EMAIL_TO
Email through your own mail serverSMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASS, ALERT_EMAIL_TO
Teams, Slack or Discord messageALERT_WEBHOOK_URL (an incoming-webhook address)
Weekly report by email and chatWEEKLY_DIGEST=1
Public status page at /status (names, up/down and uptime only)STATUS_PAGE=1
Encrypt saved API keys on diskSECRETS_KEY (any long random text; keep it safe)

Troubleshooting

Message or problemWhat to do
"Cannot reach …"The server is off, the address is wrong, or the phone is on another network. Open the same address in the phone's browser. For a tunnel address, check the tunnel is still running (it changes after a restart).
"This version of the app only connects over HTTPS"The Play Store version needs an address starting with https://. Use a Cloudflare tunnel (Step 2).
"wrong password" / "too many attempts"Retype the password you gave APP_PASSWORD. After 10 wrong tries, wait a minute.
"Your sign-in expired"The server was restarted. Sign in again under Settings.
"Could not reach … no answer within 8 seconds" when adding a checkThat address does not work from the server's computer (for example a phone-only address or 10.0.2.2). Use one the server can open.
A new check always failsOpen its address in a browser on the server's computer and compare. Placeholder addresses like example.com never work.
No phone alert arrivesYou must be signed in, alerts must be turned on in Settings, and the phone must be a real phone with the installed app. Use Send a test alert and read what it says.
The status text says "Waiting for the first run"Tap Run checks now, or wait up to a minute.
History disappearedThe data folder was deleted, or the program was started from a different folder. Restore it from a backup (see "Keeping it safe").

Keeping it safe

  • Always set a long APP_PASSWORD. Anyone with your tunnel address can reach the sign-in page.
  • Never put API keys directly in a check. Paste a curl command and the server stores keys as secrets automatically, or add them under Secrets and use {{secret.NAME}}.
  • Back up your data. Everything you save (checks, history, saved API keys) lives in the data folder next to the program. Copy that folder somewhere safe now and then. On Windows, powershell -File scripts\backup.ps1 does it for you into Documents\IntegrationReliability-backups, and scripts\restore-backup.ps1 puts it back. Keep any file that contains your passwords private.
  • Do not post screenshots that show your server address together with a password, or any key.
  • The app stores your server address and sign-in only on your phone. See the privacy policy.
  • Check names are shown on the public status page when you switch it on. Do not put secrets in check names.

Getting help

To request the server download, or to ask a question or report a problem, open an issue at github.com/kalbaapps/kalbaapps.github.io/issues (you need a free GitHub account). Say what you did, what you expected and what the app showed. Please do not paste passwords or keys.
